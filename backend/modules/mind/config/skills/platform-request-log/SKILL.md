# 平台请求日志分析 Skill（接口调用 · 页面访问）

## 〇、适用边界（先分诊，别串域）

本技能只回答**平台自身请求日志**的问题：后端接口被调用了多少次、成功率和失败数、哪些接口慢、
哪些响应码在涨、有多少登录用户/设备/独立 IP 在用平台。

- **不是 RUM**：LCP/FCP/首屏/白屏/卡顿/资源加载/页面内点击/会话 → `arms-observability`（对象 `rum_event`）。
  本域「页面访问」只是**页面上报的访问条数**，没有性能指标，不得当页面性能用。
- **不是桌面埋点**：ScanPro / AS Connect 客户端里 app 的打开、点击、扫描 → `app_usage_event`。
- **不是设备/第三方接口运行遥测**：设备侧、软件、第三方接口的运行状态 → 云平台运行日志（`cloud_es_*`）。
- **不是业务对象取数**：案例/订单/客户/内容/会员的数量与属性 → 语义层业务对象（`data-analysis` 剧本）。
  绝对不得拿请求量、页面访问量去回答「有多少案例」。
- 四域互不相同，**不得混用或相加**。判口径先看问题主语：主语是「平台的请求/接口/访问日志」才用本技能。

## 一、两个部署域（问法相同，数据不相加）

| 部署域 | 对象（object） | 覆盖站点 |
|---|---|---|
| 中国站 | `platform_request_log` | 中国站（single） |
| 国际站 | `platform_request_log_intl` | 国际站（en / jp / uk / eu 四站同构） |

- **业务名与别名一致**：国际站的每一行字典都把中国站业务名登记为别名，所以问「平台接口成功率」
  在中国站和国际站都命中本域，无需换说法。
- **两个域是两个本体**（物理表不同构）：**数据不得相加**。跨站取数必须先取一个目标站点试取，校验对象/指标/维度、列形状、时间过滤和站点符合已确认意图且无阻断告警；通过后保留试取结果并自动续取其余目标站点，不中途问用户；试取不通过立即停止扩散，不得静默换站重试。
- 站点是**取数上下文**（`site` 参数 / 会话站点），不是 SQL 维度：不要把站点放进 `dimensions` 或 `filters`。
  默认分站呈现，不自动合并。

## 二、指标与维度速览（以知识库语义层文档或 `get_metrics` 实时目录为准）

指标（中国站口径名；国际站同名带「·国际站」后缀，可用中国站名作别名问）：
`平台请求总数`、`平台接口调用次数`、`平台页面访问次数`、`平台接口失败次数`、`平台接口成功率`、
`平台接口平均耗时`、`平台接口P95耗时`、`平台登录用户数`、`平台访问设备数`、`平台独立IP数`；
故障/性能治理面另有三项：`平台慢请求数`（耗时≥3 秒的接口调用数）、`平台失败接口数`（失败接口去重 URL）、
`平台失败影响用户数`（失败请求的去重账号）。

维度：`请求类型`、`来源应用通道`、`后端服务`、`日志级别`、`请求方法`、`请求URL`、`响应码`、
`用户账号`、`请求设备标识`、`请求客户端版本`、`平台版本`、`请求日期`、`请求小时`。

## 三、口径与硬约束（照做，别自创）

1. **请求类型是分叉点**：`SERVER`=后端接口调用（有请求方法、耗时、响应码）；`CLIENT`=网页端页面访问
   （三者全空，`请求URL` 是整页 URL）。**成功率、平均耗时、P95 只对 `SERVER` 成立**；
   页面访问行的成功率为 `null`、调用次数为 0 是**正确结果**，不得解释成"数据缺失"或改分母把它算进去。
2. **成功率** = 响应码=200 的接口调用数 ÷ **有响应码的**接口调用数 × 100（0~100 的百分数，不是 0~1）。
   失败次数 = 有响应码且 ≠200。响应码的具体业务含义**以各服务接口约定为准，本域不内置映射**——
   不要臆断「3036 = 某业务错误」，只报数值与占比，需要含义时明确说「需查对应服务接口文档」。
   失败**波及面**另有两个去重口径：`平台失败接口数`（去重请求 URL）与 `平台失败影响用户数`（去重用户账号）——
   问「多少个接口在报错」「影响多少用户」必须用它们；失败次数不能替代（同一个接口失败 10 万次仍只算 1 个接口）。
3. **耗时单位是毫秒**。P95 用分位口径（`平台接口P95耗时`），均值单独报；两者不可互相替代。
   只看均值会被长尾掩盖，慢接口治理优先看 P95。**「有多少请求慢」直接用 `平台慢请求数`**
   （耗时 ≥3000 毫秒的接口调用条数），不要由 P95 反推，也不要把 P95 当成「慢请求比例」。
4. **用户/设备/IP 都是去重计数**（`COUNT(DISTINCT)`）：`平台登录用户数` 按用户账号、`平台访问设备数`
   按设备标识、`平台独立IP数` 按客户端 IP。页面访问行多数没有账号，所以「登录用户数」天然小于总请求量。
5. **IP 明细受数据权限约束**：只回计数；IP 明细按敏感数据策略脱敏或不返回。**不要试图绕过**，
   也不要在结论里拼出完整 IP。
6. **时间窗口必须显式**：日志源默认只扫最近很短的时间范围。任何计算都要给 `time_window`
   （如 `24h`/`7d`）或明确的日期区间，不要问「总共多少」却不给窗口——那等于把一个不可比的数当结论。
7. **别名归谁**：`接口调用次数`、`独立IP数`、`日志条数`、`页面访问量`、`设备数`、`用户数`、`业务类型`、
   `请求地址`、`设备标识`、`客户端版本` 这些口语词在平台内属**别的域**（RUM / ES 运行日志 / 应用使用事件），
   本域为避串味已改用带「平台」限定的名字。用户这样问时，**先分诊主语**，确认是平台请求日志再取本域；
   命中不到就让语义层回抛候选，不要硬绑。
8. **慢请求阈值是本域固定口径（3 秒）**。用户若要别的阈值（1 秒/5 秒），必须显式说明
   「本域字典只有 3 秒口径的慢请求数」，不得把 3 秒的数当成用户要的阈值报出去；
   需要自定义阈值时，用 `平台接口平均耗时`/`平台接口P95耗时` 按 `请求URL` 说明分布，不要编新指标名。

## 四、剧本

**A. 接口健康度**（「接口成功率怎么样」「最近失败多不多」）
1. `平台接口成功率` + `平台接口失败次数` 按 `请求类型`（确认 SERVER/CLIENT 口径）→ 再按 `请求URL`/`后端服务` 取失败 TopN。
2. 要定位失败原因时按 `响应码` 分组，列出各码占比；`日志级别=错误` 只作辅助（本域 ERROR 极少）。

**B. 慢接口治理**（「哪些接口慢」「P95 多少」）
1. `平台接口平均耗时` + `平台接口P95耗时` 按 `请求URL` 降序取 TopN（必须带时间窗口与 limit）。
2. 均值与 P95 差距大 = 长尾严重，报「多数请求正常但少量极慢」，不要只报均值。
3. 想看是哪个服务拖慢时，按 `后端服务` 下钻。

**C. 平台使用规模**（「多少人/多少设备在用」「请求总量」）
1. `平台请求总数` 按 `请求类型` 拆成接口调用与页面访问两类，分别报。
2. `平台登录用户数`、`平台访问设备数`、`平台独立IP数` 同窗口对比；三者口径不同，不互相替代。
3. 需要结构时按 `来源应用通道`（网页端/桌面客户端/移动端/官网/运营后台）下钻。

**D. 按应用通道/服务下钻**（「桌面客户端调了多少接口」「帮助中心服务成功率」）
按 `来源应用通道` 或 `后端服务` 过滤后取 A/B 的指标；过滤值用知识库语义层文档或 `get_metrics` 给出的业务标签，不要手写码值猜。

**E. 跨站问法**（「国际站接口成功率」「全球请求量」）
先取一个目标站点试取（优先会话当前站点，否则按服务端目标站点清单顺序首个），校验结果契约通过后自动续取其余目标站点，复用试取结果且不中途问用户；试取为空、形状不符、时间过滤缺失或权限/绑定/执行报错时停止扩散。
结果分站报数并明确「两站是两个本体，未相加」；只有用户明确要求全球合计时才相加，并标注这是跨本体求和。

**F. 故障影响面**（「多少个接口在报错」「影响多少用户」）
1. 先报 `平台接口失败次数`（量），再报 `平台失败接口数`（面）、`平台失败影响用户数`（人）——三者是不同口径，不能互相顶替。
2. 按 `响应码` 分组看失败结构，按 `后端服务`/`请求URL` 归因到具体服务与接口。
3. 报影响面必须带时间窗口；同一个接口高频失败不会放大「接口数」，需要「影响频次」时用失败次数。

**G. 页面访问行为**（「页面访问量」「哪些页面看的人多」）
1. `平台页面访问次数` + `请求URL` 取 TopN（页面访问行的 URL 是整页地址，含查询串；聚合前说明按页面归并的口径）。
2. 按 `来源应用通道`/`请求客户端版本` 看访客结构；页面访问行没有成功率与耗时，**不要报 null 或 0 当结论**。
3. 「多少人在看」用 `平台登录用户数`，但要说明页面访问行多数无账号、该值偏小。

## 五、自我校验（答前逐条过）

- 成功率分母里**没有**混入页面访问行？页面访问行的 null/0 有没有被误读成故障？
- 慢请求数和失败次数有没有混为一谈？P95 有没有被当成「慢请求比例」用？
- 有没有把「请求量」当成业务对象数量（案例/订单）回答？→ 有就撤回，改走对应域。
- 有没有拿本域数据回答页面性能/卡顿/首屏（RUM 域）？→ 有就撤回。
- 两个站点的数有没有被静默相加？→ 必须分站报或显式标注全球求和。
- 结论里有没有出现物理表名、列名、生成 SQL、数据源 id、主机/账号？→ 一律不得出现。
- 没有给时间窗口就下了结论？→ 补窗口重算。

## 六、输出规范

1. **结论先行**：一句话给出答案（如「近 24 小时接口成功率 97.9%，失败 3.4 万次，主要集中在 /star/v2/user/save_or_update」）。
2. **数据支撑**：给出关键数值 + 分母口径 + 时间窗口 + 站点。
3. **口径说明**：涉及成功率/耗时时点明「仅后端接口调用（SERVER）」。
4. **建议**：慢接口给出可执行方向（按 URL 定位、按后端服务归因）；不臆断响应码业务含义。
5. **数据真实性**：只报取到的数；取不到就说取不到并说明原因（如无该维度、窗口内无数据），
   不估算、不编造、不用别的域的数字顶替。
