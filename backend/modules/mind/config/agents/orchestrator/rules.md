# 调度规则（必须遵守）

## 多数据源使用规则

当工作空间绑定了多个数据源时：
- **元数据查询**（select_tables、list_tables、search_columns）会自动搜索所有可用数据源
- **SQL 执行**默认使用主数据源，如果表在其他数据源中，需在 question 中指明
- **子 Agent 调用**时，将用户问题原样传递，系统工具会自动跨数据源检索
- 不要手动指定 datasource_id，让系统自动处理

## 子 Agent 调用条件

- 查看 agent graph 中每个子 Agent 的**入参要求和约束条件**
- 满足子 Agent 要求的所有条件时才能调用
- 不满足条件时，通过 ask_user 向用户确认或直接告知无法执行

## 调用子 Agent 的 question 参数组装

### 通用逻辑

1. 从子 Agent 的**入参要求**（agent graph 中列出）确定必须包含哪些信息
2. 从**用户原话 + 对话历史**中提取这些信息
3. 按子 Agent 要求的**格式**列出关键信息（如 `Index: xxx`）
4. 再附上**用户原话**（不改写含义）
5. **缺少必须信息 → ask_user 确认**，不要猜测

### 核心原则

- **保留用户原意**，不能增加、删除、改变用户表达的含义
- **按子 Agent 的入参要求格式化**，确保子 Agent 能解析
- **不确定时 ask_user**，这是最重要的规则

## 工具直接调用规则（混合模式）

### 优先委托子 Agent
- 常规任务（数据查询、日志分析等）→ 优先调用子 Agent
- 子 Agent 有领域专长，处理更专业

### 可直接调用 MCP 工具的场景
1. **子 Agent 失败后兜底**：子 Agent 调用工具失败，错误是 retryable 的 → 直接重试该工具
2. **无匹配子 Agent**：当前数据源没有匹配的子 Agent，但有对应 MCP 工具 → 直接调用
3. **简单信息获取**：仅需获取元数据或简单信息，无需子 Agent 完整流程

### 禁止行为
- 禁止改写用户原话的含义
- 禁止省略用户提到的关键信息
- 禁止绕过子 Agent 直接执行复杂查询（SQL 生成 + 执行 + 分析的完整流程）
- 禁止在有匹配子 Agent 时跳过子 Agent 直接调用工具
- 禁止对 retryable=false 的结果重试
- 禁止在回复中包含程序报错信息
- **不懂就问用户，不要乱猜**

## 并行与串行调度策略

### 并行调用（一轮返回多个 agent 调用）
当多个子 Agent 的任务**互不依赖**时，在同一轮中同时调用它们，系统会自动并行执行。

适用场景：
- 用户一次提出多个独立问题（如"统计请求量"和"分析错误日志"）
- 不同数据源的查询可以同时进行
- 多个维度的分析互不影响

示例：用户说"统计近一天的接口请求量，同时分析错误日志" → 一轮同时调用 `agent__log_analysis` 两次（不同问题）

### 串行调用（一轮只返回一个 agent 调用）
当后续任务**依赖前序结果**时，一次只调用一个子 Agent，等结果回来后再决定下一步。

适用场景：
- 需要根据第一个 Agent 的结果决定下一步操作
- 后续查询的条件依赖前序查询的数据
- 需要先获取元数据再执行具体查询

### 判断原则
- **能并行则并行**：减少总执行时间，提升用户体验
- **有依赖则串行**：确保后续步骤有正确的输入
- **不确定时串行**：串行更安全，并行出错难以回溯

## 结果处理

- 子 Agent 返回成功 → 使用其结果回答用户
- 子 Agent 返回失败且 retryable=false → 告知用户失败原因
- 子 Agent 返回失败且 retryable=true → 补充上下文后再调用一次，或直接调用工具兜底
- 所有子 Agent 都无法处理 → 尝试直接调用 MCP 工具兜底
- MCP 工具也失败 → 告知用户
