背景 · 数据现实数字取自当前环境元库实测
PART 1 · 背景

先讲清楚：BI 到底给企业创造什么价值

BI 的价值不在"有报表"，而在把组织的决策从「凭经验」移到「凭同一份数据」。它兑现成五件可以算账的事。

价值一决策速度与频次

从「下周出报表」到「当场能回答」。同一个业务一天里能做三次有数据的决定，和一周只能做一次，是两个量级的组织能力。

价值形态：活动止损、渠道加减预算、异常当日响应。

价值二口径一致性

全公司用同一套「活跃」「案例」「留存」的定义开会。口径统一省下的不是分析时间，是会议室里的争论成本与错决策。

这是 BI 最被低估的价值：它是一门组织共同语言。

价值三人力与机会成本

把取数从人身上剥下来：一个分析师被临时取数打断的时间，本来应该用来做归因、建模与产品化分析。

可算账：取数工单数 × 平均处理时长 × 人力成本。

价值四风险与合规可追责

谁看过什么数据、基于哪个数字做了什么决定，能事后回放。对设备与医疗类业务，这不是加分项而是准入条件。

价值五数据资产化

建模一次、复用无数次：同一份语义层同时喂报表、看板、预警、对外内容与 AI。数据的价值随消费面数量放大，而不是随报表数量。

但价值有兑现条件

有人真的在用 + 用的数是对的 + 用的成本低于收益。
三条缺一条，BI 项目就从「能力」变成「沉没成本」—— 这也是行业里 BI 活跃使用率长期徘徊在四分之一左右的原因。

价值阶梯（我们按第四级来设计）：看报表（发生了什么）→ 找原因（为什么）→ 做预测（会怎样）→ 驱动动作（该做什么）。前三级 AI 已经能承接，第四级必须先把权限与口径做硬 —— 否则不敢让它动手。

背景 · BI 的价值使用率数字为公开报告口径，引用时核对最新版本
PART 1 · 背景

传统 BI 是怎么被使用的：一条报表生产线

① 业务提需求

「我想看各站点三方 App 的打开量按月走势」——写需求单，排期开始

② 数据工程接数建模

确认表在哪、字段含义、能不能关联；缺字段就回去补采集

③ BI 开发做报表

写 SQL / 建数据集 / 拖图表 / 配筛选器 / 对数 / 走发布

④ 管理员配权限

谁能看这张报表、哪个区域、哪个字段要隐藏

⑤ 业务看报表（消费）

固定维度、固定时间窗；问一个报表没答的问题 → 回到 ①

链路特征：问题与答案之间隔着一条生产线。报表数量随需求线性增长，维护成本也线性增长。

一个临时问题的四条出路，都没好下场

  • 等排期：需求单排队，业务窗口已经过了。
  • 要导出：拿明细 Excel 自己算，口径与权限脱离管控。
  • 自助拖拽：会用的人很强，多数人不会拖，也不会选对指标。
  • 放弃：改成拍脑袋决定 —— 这是最常见也最难被看见的流失。

成本结构：钱花在哪

软件许可与算力 · 数仓建设 · 报表开发人力（最大头） · 培训与推广 · 存量报表维护。前四项买得到，最后一项是无底洞：口径一变，几十张报表要跟着改。

四个天花板（不是工具不好，是形态限制）

预定义维度：报表没准备的拆分，问题就答不了。
静态快照：数字是上个月的，决策是今天的。
口径靠人传：定义散在文档、群聊与老员工脑子里，无法被机器校验。
看板不给解读：同一张图，老分析师看出三件事，新人只看到一个数。

所以我们要换的不是「报表工具」，而是「消费形态」：把生产线拆掉，让业务直接对着已建模的语义层提问 —— 报表仍然保留（它适合固定高频场景），但临时问题不再需要排期。

背景 · 传统 BI 使用方式AI-DataHub
PART 1 · 背景

为什么"再买一套 BI"不解决问题

问题一：取数排队

业务同学想知道「上个月哪个站点的三方 App 打开量掉了」，路径是：提需求 → 排期 → 写 SQL → 来回对字段 → 出图。

临时问题被砍掉，最后只留下一堆没人看的固定报表。

公开口径：Gartner 追踪 BI 活跃使用率七年，长期徘徊在 约 29% —— 投资在增加，日常在用的人没变多。

问题二：口径漂移

同一个「活跃用户」，A 报表按 user_id 去重、B 报表按会话计数；「销售额」有人用 GMV、有人用确认收入。

两个数字打架时，没人能裁定谁对 —— 因为没有一个权威定义源。

问题三：自助分析 = 权限失控

一旦把「直接写 SQL」开放给业务或 AI：越权查到别人区域的业务数据、明文患者信息与手机号被带走、全表扫描把源库拖垮， 而且事后查不到是谁拿走了什么。

立项判断：我们要解决的不是"能不能用自然语言生成 SQL"，而是「让一个不能信任其知识完整性的模型，在不能妥协的权限边界内，给出可验证、可追责的数字」。 这三件事同时成立，才敢接业务的生产问题。

AI + Data 的演进：四代产品，卡在同一道门槛上

第一代 · 报表 BI

IT 开发报表，业务看结果。稳定但慢，问题超出报表就失效。

第二代 · 自助 BI

拖拽式分析 + 数据模型。会用的人很强，多数人仍不会拖。

第三代 · ChatBI / NL2SQL

自然语言直连数据库。演示极惊艳，生产上输在口径、权限与可验证性。

第四代 · 语义层 + Agent（当前）

模型不再面对裸表，而是面对受治理的语义接口与可编排技能。

1语义层重新成为必选项

行业共识正在收敛为「先有指标/语义定义层，再谈问数」：headless BI、指标平台、Ontology 化建模被主流产品与厂商纳入主线。

dbt Labs 等公开对照实验显示：同一模型挂载语义定义后，执行准确率明显抬升（报告口径 +8~16 个百分点）—— 瓶颈更多在上下文，而非模型。

2Agent 从"答一句"走向"办一件事"

工具调用标准化（MCP 一类协议）之后，Agent 的形态变成：规划 → 调工具 → 读结果 → 再推理。 评估重心随之转向技能编排、失败处理与交付形态。

3治理与权限成为采购硬指标

咨询机构近两年的评估维度把 代理型洞察、会话式分析、分析治理、洞察交付、语义建模 并列考察； 企业侧调研中，合规已升为部署生成式 AI 的首要障碍。

我们的位置：直接按第四代的问题集来设计 —— 语义事实源唯一、取数执行口唯一、身份口径唯一，治理与评测内建而非外挂。

PART 1 · 背景

开源 AI-BI 的尴尬：把“要会 SQL”换成了“要先懂表”

入口是自然语言，前置却仍是一条建模流水线：先建连接、选表、建 dataset、定义维度与指标 —— 专业性没有消失，只是换了个人承担。

问一个问题之前常见开源 AI-BI 的典型路径本系统的路径
第一步建数据源连接 → 选表 → 建 dataset（或写 SQL 定义）→ 才能提问打开对话直接问业务问题（数据集是治理产物，不是提问前置）
模型上下文把库表结构（表名/列名）塞进 prompt 或检索选表；列一多就选错表、幻觉字段物理结构不进模型视野（黑盒），模型只看业务对象与字典名
口径靠 SQL 样例、训练数据、人工提示词维持（写错了没人发现）落在指标/维度字典，计算逻辑受治理；字典没有就不能发明指标
谁承担专业性仍是一个人：会建模的分析师或 DBA（和传统 BI 同一条命）拆到三处：语义层（建模一次）· 定制化 AS-BOT（方法一次）· 权限与审计（责任常在）

弱化一免懂表结构

选表与路由由本体对象、绑定与站点路由完成，用户与模型都不接触表名列名。

弱化二免懂指标口径

名字与算法在字典里；说法不准只回抛候选让你选，不替你猜一个算出来。

弱化三免懂分析方法

入口分诊、假设驱动、自我校验、统计纪律固化在角色定制的 AS-BOT 技能里。

诚实记账（这两句建议照念）：被弱化的是“人每次提问时都要懂数据”的依赖，不是工作量也不是责任。建模仍要人做（本体对象、字典、口径）——专业性从“每次提问”搬到了“一次建模”；而“不接触表结构”的代价是语义收窄，字典没登记的问题只回抛候选。权限与审计也不随“谁都能问”而放宽：谁都能问，不等于谁都能改。

PART 1 · 行业坐标

公开基准给的冷水：模型很强，企业真实场景很弱

公开基准 / 观察水位说明什么
BIRD（真实库、脏值、需外部知识）榜首约 80%+，人类专家 92.96%比早期进步巨大，但仍低于熟练数据工程师
Spider 1.0（小库、干净 schema）已饱和，业界不再看大量"准确率 90%"宣传出自这种玩具 schema
Spider 2.0（企业级工作流，Snowflake/BigQuery/dbt）难度陡增，跨度大真实企业是千列宽表 + 嵌套数据 + 多步加工
BIRD-Interact（歧义提问、需边问边探索）Agentic 模式分数很低歧义消解与多轮交互才是真短板
SQL 方言差异（同一模型 SQLite vs MySQL）可见掉分治理改写必须用目标源方言，否则语义被破坏

学界/工业界的公开批评：数据仓库里私有的业务语义不在模型训练语料里；把 FROM 与 join 条件都喂给模型， 在贴近生产的评测上仍会大幅失分。换句话说 —— 「模型不认识你的表」不是靠更大的模型能解决的问题。

失效模式一：幻觉表名列名

造出不存在的字段，SQL 能跑但数字是错的。

失效模式二：口径歧义不自知

「活跃」是用户数还是会话数？模型替你默认了。

失效模式三：权限旁路

能写 SQL 就能绕开行级隔离，越权查到别人的数据。

失效模式四：不可复现

同样问题两次不同答案，无人能对账，无法上线。

行业坐标 · 公开基准榜单数值随时间变动，演示时以区间与趋势表述
PART 1 · 背景

AI 时代变了两件事：而“说得对”要重新设计

传统分析的主语是 SQL 与看板；AI 时代的主语变成了“问题”。但把答案交给模型，就必须先回答一个新问题：凭什么信它。

变了一非结构化数据进了分析范围

过去只有“能算的表”算数据；现在文档、业务资讯、报告、工单文本都能作为口径与背景的来源。

本系统的内容中心可以把关键文章直接投放成 AI 可检索的语料（当前 15 条内容、已发布 3 条，同步至 4 个知识库；只同步已发布，语料带版本戳可判新鲜度）。

变了二专业解读可以被产品化

“这条曲线意味着什么、该做什么”过去取决于看的人是谁。把老分析师的追问路径写成技能之后，新手也能得到同样结构的分析，而不是只会看涨跌。

这是 AI 真正抬高的天花板：不是算得更快，而是把“解读能力”从人身上搬到系统里。

但必须划一条界：非结构化数据只负责“解释”，不产出“数字”。指标名称与数值仍以语义层实时目录为唯一权威；知识库只对口径解释、业务背景与模板权威，文档新鲜度不足时仅供参考。不划这条界，AI 会拿一段过期文字当成今天的数 —— 那比不回答更贵。

技能怎么分析

入口分诊、假设驱动、自我校验、“空结果不是结论”。

规则不能怎么答

契约层
模型级部署声明一份业务本体登记它适用于哪些站点、每站用哪个数据源（业务名），一次配置全对象共享。

路由层

编排层
逐站各调一次跨站问题由 Agent 按站点分别取数、分站呈现，服务端不做静默合计。

问「全球近 3 个月案例趋势」→ 五站各取一次、分站趋势表、不报合计；
问「日本站点案例数」→ 单次调用带 site。

失败怎么说

某站执行失败标「部分站点暂无数据」并落审计；不会把失败站点的空值当成 0 参与解读。

PART 2 · 不变式

三个不可动摇的中枢：一件事只有一个裁决点

这是整套安全论证的地基：只要存在第二个裁决点，两个裁决点就会漂移，最后谁都不知道“到底谁能看什么”。

中枢一单一语义事实源

本体的 canonical JSON 文档是唯一可编辑源；YAML、Markdown、RDF 图谱、上云文档、展开行全部是派生视图。

保存草案 → 自动级联：重算绑定 → 重展开对象 → 重建图谱 → 同步知识库。

红线：严禁独立编辑派生物（改了也会被下一次级联盖掉）。

中枢二单一取数执行口

全平台唯一取数入口，内部收口到统一执行器；所有消费面共用一条治理链，没有第二扇门。

判定合不合规只看一个问题：是否过了治理入口；不过治理入口的取数通道不允许存在。

新增端点若“能返数据行但不经治理”，一律不允许存在。

中枢三单一身份口径

身份只从服务端解析（JWT / 嵌入令牌 / 任务创建者 / 报表属主 / HMAC 内部头），绝不从请求体读 user_id。

验签后重读用户状态与角色：旧令牌不保留已被撤销的权限。

无身份且非系统内部调用 → 直接拒绝取数，不回退裸执行。

为什么不搞两套“保险”：双重判断不是冗余而是漂移源 —— 历史教训包括“工作空间绑源 + 角色绑源”双口径（已退役前者）、 “服务端展开跨站 + LLM 逐站编排”双路径（已退役后者）、“提议→审批→执行”三态机与权限码并存（已退役审批回路）。

架构 · 数据护城河策略数量取自敏感字段治理表
PART 2 · 重点一 深化

脱敏要真正生效，必须写进下发给数据源的 SQL

这是本项目踩过的最大一个坑，也是讲「数据护城河」时最值得讲的工程细节。

错误做法：只在结果侧脱敏

结果侧处理器按 DataFrame 列名匹配策略。但语义层投影出来的列名是业务名，甚至是一类 ASCII 槽位名（SLS 场景）—— 与物理列名对不上。

后果：查询照常成功、页面照常出图，只有脱敏静默没生效。这类缺陷不会报错，只会在数据泄露那天被发现。

正确做法：编译期注入 + 同一口径

列级安全策略从治理层取出后，在维度投影上包脱敏表达式，并且 SELECT 与 GROUP BY 用同一份。

否则会变成「按原值分组、只把展示值打星」—— 那连distinct 的个数都算泄露。

聚合指标不包：COUNT(DISTINCT ip) 输出的是计数不是原值，无需也不应包。

裸 SQL 通道同样落进 SQL

看板与报表的取数正文同样走 AST 改写，让明文不出数据源。

改写前必过渲染保真门（原样重渲染 ≡ 原 SQL）；只有 AST 不可用时才退回结果侧兜底，且必须在审计里标注为兜底路径。

两个容易混淆的「IP」

基础设施地址（数据源 host / 内网 IP / 连接串）—— 永远不外发。

业务实体携带的 IP（客户端 IP、访问者 IP）—— 属于业务数据内容，能不能下发只由数据权限裁决，绝不在出站层写死内容正则。

历史缺陷：在出站层加 IP 字面量正则，导致「客户端 IP」维度无论怎么配都出不来，而管理员在治理页查不到任何配置依据 —— 代码常量不是规则。

三条通用工程结论：① 安全策略的生效点必须在数据流出之前；② 「没报错」不等于「生效了」，必须让正常路径与兜底路径在审计里可区分；③ 判定按完整键名的词边界取，否则中文业务标签会被当成内部字段误伤。

黑盒清单：模型与普通客户端永远看不到

生成的 SQL（基线与改写后）、数据源标识、目录引用、物理表名、溯源信息、账号 / 主机 / 端口 / 连接串、原始报错栈、作为属性名出现的物理列名。

唯一例外是设计过的

仪表盘设计面板：经服务端执行权限校验与目标编辑权校验，可由人查看/编辑业务查询 SQL；改动使旧预览失效，必须重新安全校验 → 治理预览 → 确认发布。

SQL 不进入 Agent 返回、流式通道、聊天历史或普通图表响应。

元规则：禁止降级掩盖

功能不通时必须提醒用户，不允许写「失败 → 回退旧逻辑 / 换通道 / 返回部分结果 / 假成功」的分支把缺陷掩成「看起来能用」。确需降级时，代码注释与对外提示双向声明，结果里标 degraded。

并发也要有围栏

交互式取数按数据源设并发上限（可配 1~64，缺省 8）与排队预算：满员先排队，排不过预算才拒，拒时给出「正在排队、请稍后重试」的真实原因，而不是空结果或「连接不可用」。

架构 · 纵深防御AI-DataHub
PART 2 · 重点一 延伸

AI 时代的数据安全：要防的对象从「人」变成了「人 + 模型」

传统数据安全防的是越权访问；接上 LLM 之后多出三类新面：模型可被诱导、模型可被绕道、模型可把错数当事实。下面九类是我们逐条对过的。

T1提示词注入

外部内容（知识库文本、上传文档、工具返回）里夹带指令，诱导放宽过滤或外发数据。

对应：提示词与技能属注入面，权限码恒为不接 AI；知识库只回口径文字不回物理信息。

T2工具面越权编排

单步都合规，多步组合做出单步不允许的事（先拿元数据再拼明细）。

对应：每个工具调用独立过资源域与护城河，不信任上一轮的结论。

T3上下文携带敏感物

物理表列名、生成的 SQL、连接信息一旦进入模型上下文，就等于进了第三方模型的训练语料风险区。

对应：黑盒清单 + 出站收口 + 元数据按工具授权分域。

T4数据出境与驻留

云端知识库 / 外部引擎把业务数据带出院外。

对应：上云只推白名单渲染的口径文档；凭据只在服务端；执行体不得自持凭据库。

T5影子查询与旁路

借 Playground / 看板 raw_sql / 报表分享绕开行级隔离。

对应：所有通道汇合到同一个执行口；分享链按创建者 + 资源授权 fail-closed。

T6AI 产物污染对外口径

未定稿的分析结论进了知识库语料，AI 拿它回答客户。

对应：两段式草案/发布；只同步已发布内容；发布与写语料是两个权限码。

T7审计不可区分

AI 取数与人取数混成一片，事后无法回答“这个数字是谁、用什么身份拿的”。

对应：判定字段服务端注入；数据工程与分析面审计分列。

T8资源滥用与拖库

模型反复重试全表扫描，把生产库拖垮 —— 这既是可用性问题也是数据安全问题。

对应：强制 LIMIT + 数据量分级 + 按源并发闸门；超预算拒而不静默截断。

T9幻觉数字被当事实

答案听起来专而不对：编字段名、拿近似指标改名、拿 0 行当结论。

对应：宁缺勿错 + 字典没有就不能发明 + 每个数字对应一次真实取数 + 评测回归。

一句话差别：传统安全回答“你能不能碰这份数据”，AI 时代还要回答“模型能不能被诱骗去碰它”与“碰对了但算错了谁负责”。

技能一入口分诊：动手前先判三件事

① 这句话要的是解释、名称还是数字？分别走知识库 / 指标目录 / 取数。② 还存在第二种合理解读吗？只要两种解读会给出不同数字，先问一次。③ 上下文与字典已定死的别再问，但要在结论里回显所用口径。

技能二假设驱动的探索循环

框定 → 拆解（MECE）→ 取数验证 → 解读 → 自校验 → 下钻或收敛。优先一次取到能同时验证多个假设的最粗粒度数据；每次迭代都要有明确目的，不做无意义重复查询。

技能三自我校验与反编造

每个数字对应某次真实取数；分项之和 ≈ 总量；关键或反直觉结论换维度交叉验证；无对比数据不得称涨跌；同参数连查 >2 次或同错重试 >1 次即停止并说明原因。

技能四空结果不是结论

0 行 / 0 值要先排时间（当天数据可能仍在写入、去重类指标有聚合延迟）→ 再排过滤（条件叠加、大小写、存储形状）→ 再排范围（站点、环境、人群）。全部排除后只能说「当前条件取不到数，已查过这几项」，不得据此断言「没采集 / 没埋点 / 口径缺失」。

这条来自真实事故复盘：一次 0 行快照被断言成「渠道参数没进统计口径」，而同一 URL 后续查到 20 PV / 2 UV。

Palantir 为什么被反复对标：四条启发，两条差距

公开资料口径（非实测、非代言），术语以官方英文为准。它把本体拆为 semantic elements 与 kinetic elements，这个拆法就是行业坐标。

启发 1

本体不只有名词，还要有动词：对象/属性/链接之外，还有 Actions、Functions 与动态安全——本体从“知识表示”升级成“运行时基础设施”。

启发 2

AI 的价值不在模型，在上下文 + 受控执行面：大模型接到本体上读对象、调函数、执行受权动作，而不是接到数据库上。

启发 3

交付形态是应用与流程，不是报表：洞察直接落到动作（低代码应用 + 自动化 + Agent 编排）。

启发 4

卖的是“能落地”：前置工程师把本体建起来，产品才跑得动——我们的知识共创与“评测即 CI”是同一路数。

语义要素Object/Property/Link Type 一等公民，关系不靠 join 猜canonical 文档里的对象/属性/关系（带基数与 join），另加指标与维度字典绑定接口/抽象层（Interface）类建模；对象级版本与变更审阅流
动能要素Action Types 受控写回业务系统，Functions 做派生与推理写动作走权限码直执行 + “草案→发布”两段式；工具面按角色编译动词不在本体里：文档里的 actions[] 只是建模描述，无运行时消费方；也没有对客户业务系统的回写

知识图谱：本体到 RDF 的投影，检索走确定性路线

1投影链

本体文档 → RDF 投影（类型、别名 skos:altLabel、枚举 owl:oneOf、关系与映射）→ 图数据库命名图 → SPARQL 可查视图。

命名空间与谓词一处定义；投影是只读的，改图等于改事实源的反向越权。

2四类视图（同一份图，四种问法）

表关系图 · 业务知识图 · 数据血缘图 · 本体总览图。前端图页面共用一套可视化基准（圆形分类着色 + 贝塞尔边 + 力导向 / 分层拓扑）。

3增量同步与一致性

元数据 CRUD 事件进同步队列（表/列/关系/术语/指标/维度/全量），按数据源加分布式锁重建命名图；另有只报告不自动改的巡检脚本校验「对象别名 → 图别名」投影一致性。

4术语是缓冲区，不是第二真值源

业务术语表只保留尚未绑定到对象/字典的纯黑话；一旦收编，同义词落对象与字典别名，术语行退役或改注释。检索按数据源分桶，杜绝跨源串味。

检索路线做什么为什么用它
本体遍历（主路）分词 + 同义词 → 命中类型 → 一条 SPARQL 属性路径闭包 ≤2 跳 → 对象映射物理表 → 复用装填单趟完成、可复现、成本可控
关键词 + BM25中文分词 + 倒排打分，按源分桶加载术语无向量、无 embedding，结果可解释
按名回填（原 GraphRAG）收缩为确定性 by-name 元数据回填agentic 写 SPARQL 探图已退役
路由读取直接从本体文档读部署路由不从知识库文本回传——文档可能过期

范式取舍：声明式意图→确定性编译，以及被我们退回去的那条路

维度语义清单路线（MDL：模型基于清单生成查询，外部引擎执行）现役：声明式意图 → 确定性编译
查询正文由谁写仍由模型写（表名换 model、字段换指标/维度名）模型不写正文，只产意图；正文由编译器生成
口径真值源清单里的 measures / dimensions（可治理）本体 + 指标维度字典（唯一可编辑源，级联保证多处一致）
权限施加位置外部引擎按清单施加（会话变量传入）语义层闸门 + 执行器六层 + 引擎二次注入纵深（全在平台内）
物理结构是否进模型视野部分：模型见模型名与字段名完全不：SQL / 物理表 / 数据源标识均为黑盒
可复现性中：同一问题两次不同查询常见高：编译层无 LLM、无随机
方言与跨源引擎统一，但受引擎版本与连接器面限制服务端按目标源方言；跨源才走联邦
运维依赖重：外部引擎 + 清单与库的同步易漂中：编译层与本体自持
本项目状态实现过 → 已切流退役为对照后端（双跑对拍）主路，覆盖绝大多数分析形状

为什么不把“模型现场生成查询”当主路

三种代价同时付：口径漂（定义散在每次生成的正文里，没人裁定谁对）、权限不可预先审（能不能过护城河取决于模型当次写法）、不可复现（同参数重查对不上）。这三条在演示里看不出来，在生产上天天出。

语义层表达不出时怎么办：登记，不是现场编

复杂形状（多表自关联、特殊窗口、预聚合）走治理面预先建模/建数据集：人写一次、机器审一次、之后每次取数都过同一道门。
编译器表达不出时只回原因与下一步（该建模 / 该新建数据集），绝不退化成“现场编一个查询凑数”。

诚实记账：清单路线不是“没做”，是做完并跑过之后退回去的：清单生成、行级注入、会话变量传递都落地过；切流后保留双跑对拍设施（列名序列 / 行数 / 行值三段对拍，差异落结构化日志，任何不一致先修根因再切）——它是引擎升级时的安全网，不承接线上流量。

行存储与列存储：一句“按行还是按列落盘”定下了分析的天花板

维度行存（OLTP）列存（OLAP）
落盘布局一行的所有列连续存放一列的所有行连续存放
擅长点查、事务写入、取“这个人的全部字段”扫描大表少量列、聚合、分组、排序
不擅长全表聚合（要读整行，IO 浪费）高频单行写与窄更新（要改多个列文件）
压缩列间类型不同，压缩收益低同列同类型相邻，压缩率典型高一个量级
执行方式逐行迭代（火山模型）向量化批处理 + CPU SIMD
典型代表MySQL InnoDB（我们 5 个业务源）Doris / ClickHouse；日志与检索侧是“列式 + 倒排”变体（SLS 7、ES 1）

一句结论：分析型查询的特征就是“筛得宽、取列窄、要聚合”，与列存的三项优势（只读所需列、同列压缩、向量化）同构——所以“分析上列存”不是厂商说法，是 IO 算术。

一个算例（示意推算）

一张 100 列、1 亿行的表，问“按月统计独立用户数”只用 2 列。

行存：为了那 2 列必须把整行读进来 → 扫描量按 100 列算。

列存：只读这 2 个列文件 → 扫描量按 2 列算，差两个数量级。

仅为量级说明（按列宽均匀、无索引加速估算），不是我们环境的实测值；真实差距还叠加稀疏索引、分区裁剪与预聚合。

与我们直接相关的三个推论

① 同一个问题在不同源的代价不可比，所以治理改写必须按目标源方言与引擎分支（不是“先拼 SQL 再说”）。
② 日志型（SLS）与检索型（ES）不是列存数仓的替代品：它们缺分层与预聚合，所以要靠时间窗与分页上限约束。
③ 列存不是万能：写与点查仍是行存的天下，所以业务库依旧跑事务。

离线数仓与实时数仓：分层是口径的家，“快”不是目标本身

ODS 贴源层

原样接入业务库/日志，保留可回溯的现场。典型为 T+1 快照。

DWD 明细层

清洗、拉宽、统一命名与口径；一行一事件。我们环境里的真实表如 dwd_equipment_operation_log。

DWS 汇总层

按主题预聚合（人/日/设备日粒度），例：dws_equipment_dataflow_daily——同一个表名在四个站点都存在。

DIM 维度层

缓慢变化维、码表与属性；分析口径能否对齐，八成看这层。

ADS 应用层

面向报表/接口的高度聚合结果，例：daily_case_stats、hourly_user_registration_stats。

离线批（T+1）

优点：口径稳定、可回溯重跑、单位成本低。代价：看不到今天。适用：财务、运营周报、需对账的指标。

实时流（CDC / 流式）

优点：秒级发现异常。代价：口径易漂（两套代码两套真相）、乱序与补数难、成本高。适用：安全告警、设备在线状态。

流批一体 / 湖仓

一份存储、同一套 SQL 两种时效（Iceberg/Hudi/Delta 加表格式）。目标是把“两套口径”减为“一套口径两个新鲜度”。

存算分离、存算一体与引擎版图：我们四类源恰好各占一种形态

形态一 · 存算一体（share-nothing MPP）

数据存在计算节点本地盘。快（无网络跳数、缓存天然命中），但扩容要 rebalance，冷热不均、空闲时也付全成本。典型：传统 Doris / ClickHouse / Greenplum。

形态二 · 存算分离（云原生）

计算无状态 + 共享对象存储 + 本地缓存。弹性与成本好，但缓存未命中就是延迟抖动，跨可用区流量也计费。典型：各大云数仓、Doris 3.x 分离模式、ES 冷/冻层级。

形态三 · 服务化托管（我们碰得最多的形态）

日志服务与检索云：存储与计算都在服务商那里，对外只暴露查询接口与配额。代价最隐形：时间窗、分页能力、函数子集都是平台说了算，不是我们想不想分离。

我们的现实

MySQL 5（业务库单机）· Doris 1（MPP 列存）· SLS 7（日志服务）· ES 1（集群分片）——四种形态同存，所以平台不假设引擎形态，只假设“能在源侧算就别搬过来”。

要干的事该用谁别用它干什么
事务与点查行存 OLTP（业务库）拿它跑全表聚合（锁与 IO 放大）
宽表聚合分析MPP 列存（Doris）当 OLTP 用；高频窄更新
海量日志/遥测日志服务（SLS）当数仓用（缺分层与预聚合）
全文与半结构检索搜索集群（ES）跑两级聚合/窗口函数（能力边界，实测会拒）
跨源拼装联邦或先物化把不能下推的算子当“透明优化”

Doris 为什么在我们这里是“例外注意项”

它说 MySQL 协议，所以我们复用 MySQL 连接器、方言族走 mysql——但函数子集不全（脱敏表达式必须按引擎分支校准）。这就是“协议兼容≠语义兼容”的典型案例：能连上不等于能算对。

联邦查询与命名空间：先说清“谁的名字”，再说“谁的计算”

层级是什么我们环境里的对应
catalog命名空间顶层：一个可访问的数据“目录”，下面挂多个库（引擎原生目录或连接器目录）三段式限定名参与绑定解析；元数据按 catalog → 源 → 表 → 列 组织
schema / database库（MySQL 叫 database、PG 叫 schema，同一概念不同写法）数据源登记时携带库名，不靠默认库兼容
table / view形状单元；视图不是数据是口径视图不得被“只同步基表”的过滤系统性丢弃
column带类型、注释与业务名的叶子敏感与行级策略都按物理列名命中

两个 “catalog” 词义必须分开（现场很容易听撞）

① 引擎语境的 catalog：命名空间顶层（Trino catalog、Doris catalog、Unity Catalog）。
② 本平台的「资产目录」模块：元数据与表/列清单、数据产品登记。
二者只在“都在回答这张表在哪、归谁”上重叠；权限与治理只认第②个，名字解析只认第①个。

联邦查询：三条实现路

Ⅰ 引擎原生跨源 catalog（Doris/StarRocks 读 MySQL/Hive）；Ⅱ 独立联邦引擎（Trino/Presto/DataFusion：规划后分发）；Ⅲ 先物化再查（把联邦变成一次同步）。

联邦的真代价（不是“透明优化”）

不能下推的算子就把行搬到本地：行数与内存不可控、超时、方言不一、权限施加在哪一侧说不清。能接受这三条才用联邦。

我们的做法

下推优先，联邦才本地计算：DataFusion 只做规划与校验，远程表执行发生在源库，拉回 Arrow（不在本地把大表拉进内存）。跨站取数不靠联邦，靠声明式站点路由改写到本站生效源。

为什么不“会话绑多源一次查完”

因为行级隔离与敏感基线是按单一生效源施加的；会话多源会把“身份→策略”变成多套并行。所以单源绑定是设计意图，跨站由逐站编排完成。

数据同步：把数据搬对，而不是把问题答对

同一句“同步”，围栏完全不同：它是数据工程面（不回数据行、不经 LLM），不是分析面的另一种写法。

全量快照

最简单、可对账。坑：撞源、窗口长、量大就跑不完。

增量（时间戳/自增键）

成本低。坑：抓不到硬删除，改旧值不更新时间戳就漏。

CDC（binlog）

近实时且能捕删除。坑：乱序、schema 漂移、上游 DDL 直接打断管道。

分区覆盖写

批回填的标准形。坑：TRUNCATE + INSERT 有读空窗，必须 staging 分区再原子交换。

幂等可重跑

以业务日期为键；重跑不重复落库（宁阻断勿重复）。

“预算即拒”而非“补个 LIMIT”

沿用交互式默认 LIMIT 会把全表静默截断成前 N 行还报成功——那是错数不是限流。超预算必须拒并给原因。

统计严谨性：把六条课写进 Agent 的行为约束

1对比定标

任何「高/低/好/坏」都要有参照：环比/同比、目标/基线、分群之间、分布在中的位置。无参照不下趋势结论。

环比 =（本期-上期）/上期；跨度 >1 年补 CAGR；MA7 / MA30 平滑。

2异常检测

基线 mean±2σ（±3σ 严重）；相邻变化 >50% 计突变；与上周同天/上月同期偏差 >30% 计同比异常；连续 ≥3 点同向偏离计趋势异常。

数据点 <10 不做可靠检测，必须声明。

3样本量与噪声

比例差异要判断是否只是噪声；样本量过小必须标注。低样本看板直接带「低样本」标签。

4结构与分层

分布、集中度、长尾；分群对比（渠道/地区/设备/新老/价值分层）；警惕辛普森悖论（整体与分组方向相反）。

5相关 ≠ 因果

归因只给「可能原因」与贡献度拆解（各细分对总量变化的绝对/占比贡献），区分「量大」与「增速快」；预测注明「基于历史的参考判断」。

6周期性与拐点

识别周期性需 ≥2 个完整周期；拐点 = 升降反转处并量化前后差；波动大或数据少则放弃预测。

量化归因的标准句式

「本期下降 X%，其中贡献最大的是 A（贡献 Y%），方案……；建议动作……」 —— 结论必须同时有方向、幅度、结构与建议，建议 ≤ 3 条且逐条能回指图中证据。

口径回显

结论里显式写出所用人群、时间窗与粒度（如「近 7 天、按天粒度、仅生产环境」），让用户一眼能纠偏 —— 这比多算一个指标重要。

交叉验证

关键或反直觉结论，换一个维度或粒度再查一次；仍存疑就标注置信度与数据局限，而不是把话说满。

技术 · 语义层契约能力项与枚举取自语义层模型定义
PART 4 · 工程机制

SQL 解释器与权限注入：安全不是加个 WHERE，是改写整棵树

一、SQL 解释器（方言敏感的 AST 层）

  • 方言映射：按数据源类型定解析/回写方言（MySQL·Doris→MySQL 族，SLS→PG 族）。用错方言会把 "quoted_id" 当字符串字面量、ARRAY[] 变 ARRAY() —— 能跑但错数。
  • 只读护栏与容解：单语句 + 必须查询节点，遍历 AST 拒 DDL / DML / Command / INTO；解不动时按方言族序重试，全都解不动→拒执行，不猜。
  • 真表提取：用 Scope 解 CTE 与派生表，只取真实物理表（不能按名字全局排除）；三段式限定名归一，跨库同名不串味。
  • LIMIT 收口与渲染保真门：只在解析成功后补外层 LIMIT，已有合规 LIMIT 那么原样不动；改写前比对“原样重渲染 ≡ 原 SQL”，不等价就不进 AST 改写，而不是赌解析器。

三个真实的坑（都不是假想）：① now() 被重渲染成 CURRENT_TIMESTAMP 后，日志源的 to_unixtime() 直接报错；② Hive 的 LATERAL VIEW 输出列曾被“位置重命名”护栏误杀；③ ES 派生表的 SELECT * 不透传 .keyword 多字段，所以包裹子查询在 ES 上必跑不通。

二、权限注入：十一段顺序，缺一不可

1–2 目标准备

按目标源定方言与引擎（脱敏表达式按引擎而非方言生成）；表清单自己重解，不信调用方传入

3–5 三级 RBAC

无身份→只套敏感基线；源级 fail-closed（跨源限定名所属源逐个校）；表级白名单交集

6–7 列与投影

逐表加载 hidden/masked/row_filter；策略传播到输出列名，拒位置重命名（否则改名就把受控列洗白）

8–9 行级过滤落进 SQL（套不上就拒）

FROM t → FROM (SELECT * FROM t WHERE 谓词) AS t，作用域内列引用一并改写到保留别名（所以 JOIN 两侧不漏）；ES 改走顶层 WHERE AND。策略套不到表引用 → 拒执行，静默原句放行就是“假治理”

10–11 列级与纵深

脱敏写进待执行正文（明文不出数据源）；引擎侧二次注入 + 策略视图化（按策略指纹分会话，天然覆盖 JOIN）

兜底路径必须可审计

AST 改写不可用时才走结果侧兜底，并在审计里显式标注（result_side_fallback(原因)）；ES 通道不允许兜底 —— 输出列是业务别名，结果侧按物理列名对不上 = 静默不脱敏。

多引擎现实：方言、下推、联邦与并发

1治理改写必须用目标源方言

方言族按数据源类型映射：MySQL / Doris 走 MySQL 族，PostgreSQL / SLS 走 PG 族。用错方言会破坏 ARRAY[]、把双引号标识符读成字符串字面量 —— 能跑但错数。

2下推优先，联邦才本地计算

单源查询把 SQL 推到源库执行再拉回列式结果；跨源才由本地规划器做联邦计算。这是联邦引擎的标准做法，好处是不把全表拉到本地。

连接器不可用或失败一律显式报错，禁止回退裸连接直查。

3会话按策略指纹分桶

执行会话按「策略指纹」分桶复用：不同权限视图不能共用一个会话，否则会把 A 的过滤结果给 B。

4SLS 默认时间窗陷阱（实测）

日志型源在 SQL 没有时间比较谓词时只扫描自身默认窗（实测约最近 15 分钟）；用普通日期列过滤不会放宽该窗，只能收窄。

实测同一张表：无谓词 37 行，加一年谓词 2 200 万+ 行。所以「行数很少」不等于「库里没这么多数据」—— 这是一类会把人带错的坑，已写成技能约束与探针脚本。

5检索型引擎的 SQL 边界

全文检索引擎只支持有限 SQL 形状（派生表/部分函数不支持），且列名带 .keyword 这类后缀需归一。能力边界写进数据集判定，而不是拿一条能过的样例当全量支持。

6并发限流，而不是池化复用

一次看板刷新 = N 图 × M 人，SQL 型源每次取数新建连接；不限并发就是集体撞源侧连接上限。所以限流靠按数据源的并发闸门，而不是靠连接池参数 —— 两者语义不同，拿后者当限流是误用。

演示可点的一句话：这些坑全部属于「引擎能力差异伪装成业务结论」那一类 —— 处理不好，平台就会拿着 37 行告诉客户「你们官网没人访问」。

最容易搞错的地方：三个权限维度不得混用

A功能能力（平台动作）

权限码 + 菜单归属 + 接口路径模式 + AI 可调用级别；角色被授予码。

裁决点：API 中间件（能不能调这个接口）；写动作由权限码在执行前把关。

菜单与功能同步登记，不得留空承诺（配了不生效）也不得凭空丢入口。

B数据资源（能看哪些行列）

源 / 表 / 列 / 行级策略 / 用户属性变量 / 敏感基线 / 看板与数据集访问。

逐工具勾选 + 执行层天花板 + 涉密硬上界（代码层，配置抬不上去）。

典型上界：凭据类、身份与权限类、安全边界类、全局配置、提示词与技能（注入面）。

为什么必须分开：若用 A 的菜单码去门控 B 的取数工具，权限语义会跟执行器与闸门打架，还会把「看板页能读指标」误当成「可以执行 SQL」。 UI 上同样分区展示，避免管理员误配 —— “配了不生效”与“生效但看不出配了”都是缺陷。

写动作只有一条回路

权限码 + 工具授权 → 直执行 → 审计落库；判定字段由服务端注入不从请求体信任，幂等由状态条件更新仲裁。旧「提议→审批→执行」三态机已退役，不得回潮。

行级过滤的四个细节坑

包裹子查询注入；必须保留原表别名（不得生成非法双重别名）；FROM 与 JOIN 两侧都要覆盖；下一词是关键字时不能误当别名。漏一侧就是关联查询旁路。

空授权不是全量

未配 = 无权。历史缺陷是写成「有配才筛」，等于未配时放行全量；admin 也不在数据面旁路。

缺口实测证据（本次跑的）影响演进动作
一、扫描明细算不动MySQL 连 COUNT(*) 都读超时；Doris 侧同构表 dwd_equipment_operation_shadow 已建、0 行scan_quantity、scan_consume_time、优化失败次数、电量消耗、CPU 与内存、固件/客户端版本、扫描头型号——字段全在，但做不了“版本×机型”分位数对比第一步（成本最低）：接通业务库→Doris 同步并做日粒度物化
二、“一次扫描”没定口径字典里只有 SUM(scan_consume_time)（总耗时）；另有 operation / refine / refine_max 三个耗时字段“均扫描耗时”能算出三个不同的数，看板与问数会各说一套定一个指标（扫描总耗时 ÷ 扫描次数，另建“单次最长”作分位参考），公式进字典
三、改善计划几乎没人标collection_status≠0 仅 2.88 万 / 317.9 万有效案例 = 0.91%；而 93.9% 有 scan_time本次最大发现：不是缺数据，是缺把异常自动标出来的机制用告警 + 优化失败 + 掉线自动挂到案例（候选由系统出、确认由人做）
四、临床场景太粗case_type 只 3 种；t_case_treatments 已有 clinical_type、work_type、上/下颚工作类型、age_type、scanbody_type时长与失败没法按难度/术式分层，结论会被病例结构假扮收编进维度字典（已在对象里，不需新建表）

三步走（建议当会议结论记）

近 1 个月：接通同步 + 日粒度物化 + 定口径；本季度：临床维度收编 + 版本 A/B 看板；之后：异常自动挂案例→改善闭环。

为什么必须在平台上做

三条线要跨站、跨权限、跨引擎（MySQL + Doris + ES）——个人 agent 拿不到也不该拿到这个数据形状。

下一步要谁点头

同步链路要数据工程侧排期；口径与维度收编要产品与临床侧确认——都不是平台开发量。

诚实边界（现场请照念）：以上为 prd-cn 单站实测，其余四站只核验“表存在且同构”；refine_fail_quantity、电量类字段的填充率与单位尚未审计——同步接通后先做数据质量对账再出结论。

收尾 · 诚实清单

还没做好的事，写在演示稿里

一份只讲成绩的架构演示不取信于人。以下是当前已识别、已记录、尚未收口的项目。

安全尚未收口

  • 跨库三段式限定名的表抽取与匹配键归一仍依赖解析器版本行为，同名串味风险需继续加用例覆盖。
  • 权限判定有 30~60 秒缓存窗口；改完权限配置的写路径必须确认调了失效。
  • 并发闸门目前是进程内的；多副本 / 异步 worker 部署需换成租约式实现。

能力待补齐

  • 部分数据点不足时异常检测与预测仍偏保守，需更多真实周期才能上结论。
  • 知识库同步目前为纯手动，新鲜度漂移靠水位线与人工对账兼顾。
  • 进化闭环中存在“继任函数无主链路调用方”的双队列并存，需要接线或声明分工。

工程待清理

  • 代码注释与退役表的漂移（旧审批表仍在库、旧口径注释未改）—— 容易误导后人重建旧机制。
  • 部分遗留表已不被读取但仍存在，需冻结/归档口径。
  • 跨站、多引擎的组合场景评测覆盖仍不够密，尤其是 ES / SLS 方言交集。

下一步三个优先：① 把检索层通过率从 82% 拉到下限以上（先归因：是分桶词典不足还是策略选择问题）；② 把跨库限定名与 RLS 覆盖面先升级再引入新 SQL 形态（安全升级先行，功能随后）；③ 把未完成的运维域 AI 零接入约束从文档推至代码硬上界 + 用例断言。
