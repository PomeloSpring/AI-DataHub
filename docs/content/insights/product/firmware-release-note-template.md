## 一、为什么发布说明属于质量体系

版本号必须能让人判断"这次变更是否触及注册内容"——这是审查要点里的实际要求。因此发布说明承担两个作用：

1. 给用户与售后的**操作依据**（要不要升级、升级后注意什么）；
2. 体系内的**分发记录**（哪个版本、发到哪些机型、生效范围、验证留档）。

写不清楚，两头都出问题：用户升级后行为变了没人知道，审评时拿不出变更判定依据。

## 二、变更分级：五个判定问句

按顺序问，任一为"是"即按**重大软件更新**处理（需走变更控制与相应注册路径）：

1. 是否改变了**预期用途**或适用范围？
2. 是否改变了**输出几何**（拼接、边缘识别、补洞等算法的输出结果会不一样）？
3. 是否改变了**安全相关功能**（提示、拦截、权限、数据接口）？
4. 是否改变了**算法结构**或**训练数据分布**？（AI 部分的关键判据）
5. 是否影响**与其他设备的互操作**（文件格式、坐标约定、接口协议）？

全部为"否"→ 可归为轻微更新（缺陷修复、文案、性能优化且不改变输出），走简化评审。

> 注意第 4 条的细分：同结构换数据重训属于**数据驱动型**更新，需看新旧性能评估有无统计学差异；有差异才算重大更新。这一判定必须留书面记录。

**变更级别**：重大软件更新 / 轻微软件更新（判定依据见下）
**建议升级窗口**：
**是否需停机/重新标定**：

### 一、本次变更
- 新增：
- 优化：
- 修复：

### 二、变更级别判定

## 四、写作纪律（四条硬要求）

1. **不写"大幅提升精度"这类无口径表述**。要么给出测试条件与数值（并按 `regulatory-standards-map` 的模板表述），要么只写"优化了 X 场景的稳定性"。
2. **行为变化必须显式列出**。用户发现结果和以前不一样却不知道为什么，比不升级更糟。
3. **已知限制不许省略**。宁缺勿错——写清"暂不支持的场景"能省掉大量售后。
4. **不留假数据**。模板里的【由X填写：…】是人工填写位，未填真实验证结果与文件编号前不得对外发布；它表示"此处由谁填"，不是可以带着上线的半成品标记。

## 五、版本命名建议

采用能表达变更级别的三段式（示例，仅示意口径，需与你们现行命名规则一致）：

```
主版本.次版本.修订号
  │      │      └─ 轻微更新：缺陷修复、文案、不改输出的性能优化
  │      └───────── 功能更新：新增能力但不改变既有输出几何
  └──────────────── 重大更新：触及预期用途/输出几何/算法结构
```

命名规则文件本身要走受控管理，任何调整需变更控制批准。本公司现行命名规则以质量部受控文件为准，本文不代列文件编号与生效日期。

## 六、发布后的动作

- 分发记录归档（版本号、目标机型、批次、生效时间、接收确认）；
- 售后与客服同步"行为变化"要点，避免一线答不上；
- 生产后信息监控：投诉、偏差、返修在两个观察周期内的变化，回灌到下一轮风险评估。
