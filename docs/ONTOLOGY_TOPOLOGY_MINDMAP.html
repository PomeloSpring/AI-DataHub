3业务本体的真实判据：管几个源本体，决定它有没有存在价值

这是本轮最关键的一条认知修正 —— 判据不是"跨不跨站"，而是"跨不跨源本体"。

没有增量 —— 对象、属性、关系全是源本体的复述。 该情形下应当直接用源本体问数，或把"业务本体"降级为别名/口径层， 不要维护两份同构模型（历史 27 对象 × 5 站 = 135 行机械复制就是这类错）。 情形二 · 业务本体管 N 个源本体（N≥2） 源本体 MySQL 业务库 源本体 Doris 源本体 SLS 日志 业务本体 职责 = 描述源本体之间的关系 + 跨源衔接键 + 统一业务名 结论：这时业务本体才有存在价值 —— 它的图谱是"跨源关系网"， 源本体各自只看得见自己库内的表列，跨源关系在源本体层无法表达。 现网诊断 · 联耀业务本体落在"情形一" ① 它只挂 datasource_id = prd-cn 一个源（5 站是同一套 schema 的同构展开，不算多源本体）； ② 51 条 links 全是同库对象之间的关系（company→case、user→case…），没有一条跨源关系 —— 所以它的图谱确实就是"源本体 → 源本体"的图； ③ 数仓（Doris 源本体，4 对象）与日志（ARMS RUM 源本体，1 对象）已经在库里，但没有任何一条边把它们和业务本体连起来 → 这才是"跨源"真正缺的那一半。
由判据推出的三件事
  • 不要给 5 个同构站点各建源本体（实测 16/17 对象五站列集合完全一致）—— 那是"情形一 ×5"，纯复制。
  • 业务本体要往"多源"长：把 Doris 数仓源本体、SLS 日志源本体纳进同一个业务本体的管辖范围，并登记跨源关系边（第 5 节模拟图就是这个样子）。
  • 跨源关系需要"衔接键"：业务库 case_code ↔ 数仓汇总 case_code ↔ 日志 caseCode，这类映射在源本体层各自存在，只有业务本体层能把它们连起来（M3 计划的 links[].cross_source）。
  • 承载（取数路径）本质是"跨源关系"的特例：同一概念在不同源的副本 —— 所以它该并入业务本体的关系/规则表达，而不是单开一套配置面（呼应第 2 节）。

4一次问数走的逻辑过程（按新判据修订）

以「全球用户数」为例。紫色序号 = 本轮按你的纠正改写的环节。 黑盒纪律不变：datasource_id / 物理表列 / 生成的 SQL / 账号 IP 全程不进 LLM 视野。

1

输入分流 + 资源绑定（唯一裁决点）

寒暄/无效输入本地直答；业务问题下发 Agent。resource_guard.bind_resources 返回 available_sources —— 只由用户角色授权决定，可查站点是它的派生视图，空授权 fail-closed。

2

提示词注入「数据源拓扑」段 本轮改写

规则③：默认分站呈现、不做跨站合计（这是缺省口径，不需要用户交代）。旧文案"合计请标注各站合计≠去重全球数"已删 —— 那是在鼓励模型去做那个合计。不再提 authority，改为"该指标编排了哪个源就去哪个源"。

3

目录检索 get_metrics

对象 + 指标 + 维度 + relations + deployments（+ 可选路径清单，按授权裁剪；被裁条数只写服务端日志）。 名字与口径的唯一权威是这里，知识库只补口径解释。

4

名字解析（确定性，宁缺勿错）

字典精确名 → 字典别名 → column_map → 物理列业务名 → 物理列名兜底，每档记 resolution_source 入 provenance。 包含式模糊只回抛候选，被拒词落 adh_alias_suggestions。

5

判定"要不要去重" —— 看用户怎么说 + 指标怎么编排 本轮改写

说法结论依据
"全球用户数" / "有多少用户"按站点分组，不去重 缺省口径。维度编排里站点是默认分组维度；agg_type=COUNT_DISTINCT 且用户没要总数 → 不跨站合并
"总数" / "不区分站点" / "去重后"跨站去重单值 取该指标编排的去重源（字典 datasource_id+target_table 指向数仓汇总表）
"今天" / "实时"去重源不参与新鲜度排除（t_plus_1/lagged 不答"今天"）
6

选源与回落：按编排顺序逐级尝试 本轮改写（替代 authority 判定）

候选源顺序 = 字典编排（数仓汇总） → 承载可选路径 → 站点业务库
  命中即取；该级不可用（无权限 / 无表 / 执行失败）→ 下一级 + 标 degraded=true
  全部落空 → fail-loud 回抛业务名候选（不猜、不相加充数）

权限不可见的源 = 作用域裁剪（对用户不提）；有权限但失败 = 降级（必须显式标）。两者必须可区分。

7

绑定解析 → SQL 编译

同构站点走 deploy_sites 展开；异构源走承载指向的源本体对象（复用同一解析口）。 跨对象引用用「对象名.业务名」限定名，JOIN 路径由本体 links ≤2 跳 BFS 解出，无路径回抛不猜 join。

当前卡点 51 条 links 只有 11 条能走通，且跨源关系 0 条 → 跨源问题在这步直接无路可走。

8

七闸门 + 权限施加（不可旁路）

identity / permission / preflight / proposal / approval / execute / audit； permission_enforcer：敏感字段基线（对 admin 也生效）→ 表 RBAC → 列级 hidden/mask → RLS 行过滤（包裹子查询注入，保留别名，FROM/JOIN 两侧都覆盖）。

9

执行与序列化

统一取数口 semantics.execute；重名列经 df_serialize 无损消歧；单次批量 ≤8 个 intent，展示 >200 行截断且禁止对截断行求和。

10

呈现与归因

  • 分组路径：每站一行 + "未做跨站去重"；去重路径：单值 + 口径时效（"数仓汇总，T+1，不含今天"）。
  • 降级：degraded=true + 业务名文案 + 服务端 WARNING；不得拿各站相加冒充全局值。
  • provenance 记 carrier_bucket + path_used_reason（declared / dict-ordered / fallback / site-detail / degraded-fallback / no-path），审计能分辨走了哪条。
  • 适合可视化时输出 ```chart 块，样式走字模库统一管线。

7术语对照（这几个词最容易乱）

词准确含义不是什么 / 注意
源本体 kind='source'某个数据源物理表列的语义投影，物理形状的唯一事实源 不是"低级模型"。业务本体只管 1 个源本体时，它基本就是源本体的复述（第 3 节判据）
业务本体 kind='business'跨多个源本体的统一业务描述 + 源本体之间的关系网 它的增量价值只在跨源；跨站同构展开不算跨源（那由 deploy_sites 管）
承载 / 取数路径同一概念的一条可取数路径：哪个源、对应哪个源本体对象、什么粒度与新鲜度 不携带优先级、不携带权威位（按本轮纠正）；也不是物理表映射（那在 adh_ontology_bindings）
字典编排指标/维度行声明的口径与取数位置：datasource_id + target_table + formula_dialects + agg_type 这才是"数仓优先"的落点；certified 已表达"单一事实源"，不需要再造 authority 位
分站呈现每站一行/一表，各站独立口径，不相加。是"全球 X 数"的缺省呈现 用户明确要"总数/不区分站点/去重"才切去重路径；没去重源时如实说"没有去重后的全局值"
作用域裁剪 vs 降级裁剪=没权限，路径对模型不可见，对用户不提；降级=有权限但失败，必须 degraded=true 显式标 把"缺权限"讲给用户是越界；把"执行失败"藏起来是掩盖缺陷。两者必须在审计中可分辨
快速路径 quick_path知识管理里已上线的"查询方案指引"：触发词命中 → 说明文本注入提示词 它是提示词级、LLM 自由裁量，不是确定性选路；现在却带 priority/datasource_id → 与承载/规则重叠，待收敛
规则 rules / 场景 scenarios本体层的走法偏好(path_preference)、可用性(availability)、口径告诫(caveat)；多步分析剧本 M4 未落地。落地时每种 kind 必须有已登记消费方，否则激活阻断（防"配了没用"）
跨源衔接键同一实体在不同源里的对齐列（case_code / equipment_code / user_code），投影为 linkableVia + joinKey 只用于图面与多步编排提示，不进 planner：语义层 JOIN 仍锁同源 ≤2 跳
同构站点部署 deploy_sites一份契约 × N 站，取数按站点把生效源改写到请求站 只管同构复制；跨源/跨层一律走承载。两套不混用，可并存
