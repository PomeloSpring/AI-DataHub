The service is organized in a layered FastAPI architecture under `services/dataflow/`:
- `main.py` bootstraps the FastAPI app on port 8003, mounts CORS, and registers four routers: `/api/sync`, `/api/workflow`, `/api/scheduled-tasks`, `/api/notification`.
- `api/` contains thin request/response handlers (Pydantic models + FastAPI routers) that delegate to services; each router file maps one domain (sync, workflow, scheduled, notification).
- `services/` holds business logic: `sync_service.py` (CRUD over `adh_sync_tasks`, `adh_sync_logs`, `adh_scheduled_tasks`, `adh_scheduled_logs` via shared DB pool), `dag_generator.py` (renders Python DAG source from templates like `mysql_to_doris`, `generic_full`/`generic_incremental` and writes them to Airflow's DAGs folder), `airflow_client.py` (httpx-based client wrapping Airflow REST v2 API for DAG trigger/status/logs), `workspace_service.py` (reads workspace/datasource/MCP server metadata from the metadata DB), plus `notification_service.py` and `scheduled_task_service.py`.
- `tasks/` defines a Celery application (`celery_app.py`) with Redis broker/backend, two queues (`default`, `scheduled`), and a Redis-backed multi-instance lock for Beat so only one scheduler runs. `executor.py` and `beat_schedule.py` contain the actual worker tasks; `notification.py` handles alerting.
- `mcp_server.py` exposes an MCP-compatible tool surface (`create_sync_task`, `run_task`, `get_task_status`, `list_tasks`) that composes `dag_generator` + `sync_service` + `airflow_client`.
- Dependency direction is strictly top-down: `api -> services -> external clients (Airflow REST, shared DB)`; `mcp_server` reuses the same services. The Dockerfile builds a `python:3.11-slim` image, installs shared and per-service requirements, sets `PYTHONPATH=/app`, and runs uvicorn directly.
