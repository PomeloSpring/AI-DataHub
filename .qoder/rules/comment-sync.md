# 注释与行为同步（防注释漂移）— 强制规范

> 注释/docstring 描述的是"代码在做什么、禁止什么、失败时怎么办"。**需求或行为一变，描述它的注释必须同批更新**——
> 过时注释不是无害的字，是误导源：它让维护者、评审、AI 助手按**已不存在的分支**做决策。
> 注释漂移视同缺陷，必须修复，不得以"注释而已"放行。

## 1. 同批更新纪律（行为变 → 注释变）
- 任何改变行为的提交（增删分支、改变优先级顺序、改变失败语义、增删降级/回退/兜底路径、改默认值/契约），
  **必须同批检索并更新**描述该行为的注释、docstring、模块头注释与 README/设计文档对应段落。
- 高危注释类型（漂移后误导性最强，逐一核对）：
  ① **流程/优先级列表**（如 `Execution priority: 1. A ... 2. B fallback`）——分支删了列表必须删；
  ② **失败语义**（"失败→回退 X"/"兜底到 Y"/"重试 N 次"）——回退被禁后不得残留"回退"字样；
  ③ **禁令声明**（"禁止 X"/"唯一通道是 Y"）——见 §2 反向校验；
  ④ **契约说明**（docstring 的 Args/Returns/Usage 与真实签名、真实行为不一致）。
- 需求变更（例："以后不允许回退"）落代码时，改动清单必须含"清除旧口径注释"一项；
  用关键词全库检索核对存量：`fallback / 回退 / 兜底 / 降级 / priority / deprecated / 旧逻辑`。

## 2. 名实一致（双向校验）
- **正向**：注释说有的行为，代码必须真有；
- **反向**：注释说"禁止/不存在"的行为，代码必须真的禁止（有对应 raise/校验 + 测试锁定），
  不得只把禁令写在注释里当摆设。
- 不得用注释"声明"治理约束代替代码落地（如"禁止降级直连"必须有 fail-loud 实现与门禁用例，
  见 `security-guardrails.md` §11 / `no-silent-degradation.md`）。

## 3. 案例（本条规则的由来）
- 2026-10：DataEngine 直连回退分支按"禁止降级直连"指令移除后，4 处注释未同步
  （`query_executor` docstring "Direct execution — fallback (no RLS)"、`get_connection` "直连兜底"、
  `engine_client`/`datafusion_dialect` "引擎报错 → 上层回退 MySQL 直连"），
  继续描述已删除的回退路径，直接误导后续架构评审——把**已禁止的回退**当成现行设计讨论。
  修复成本 5 分钟，误导成本是整个评审结论作废。此即 `no-silent-degradation.md` 的文档侧镜像：
  代码不许静默降级，注释也不许静默过时。

## 4. 落地与自查
- 提交行为变更 diff 时自问：**"有哪些注释还在描述旧行为？"**——改动函数的 docstring、模块头、
  同主题常量/配置注释逐一核对。
- 评审时看到注释描述分支/优先级/回退/兜底，随手核对代码是否真有该分支；
  发现漂移视同缺陷随手修；需回归时用测试锁**行为**，不锁注释文案。
- 收尾口径：行为变更的 PR 里，"注释同步"与"测试同步"同等属于完成标准——
  只改代码不改注释视为未完成（与 `fde-evolution.md` "只加功能不加用例视为未完成"同格）。
