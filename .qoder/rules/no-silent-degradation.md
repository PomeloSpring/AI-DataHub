# 禁止降级掩盖（功能失败必须显式暴露）— 强制规范

> 降级逻辑不是遮羞布。功能做错/做不通时，**提醒用户（显式报错或可见提示）**，而不是擅自写降级分支把失败掩藏成"看起来能用"。
> 静默回退会让缺陷逃过所有人眼睛，直到给出错答案才暴露——这比直接报错危害大得多。

## 1. 默认行为：失败即暴露（fail-loud）
- 新增/修改功能时，**禁止擅自添加"失败→回退到旧逻辑/另一通道/返回部分结果/假成功"的降级分支**，除非需求明确要求且写明触发条件与对用户的影响。
- 功能不符合预期时，正确做法是：抛错或返回带原因的错误提示，**提醒用户**（前端可见文案 + 服务端日志），然后修复根因——不是写降级让它"不报错了事"。
- `except` 捕获后只 `return 空/默认值/True` 视为掩盖；必须携带可诊断信息（错因、触发条件、降级事实）方可对外返回。
- 降级分支若确属需求要求，必须在代码注释与对外提示中**双向声明**（用户能看到"当前处于降级模式"），并在结果中标注（如 `degraded=true`）。

## 2. 与既有 fail-safe 的边界（不得拿 §4 当挡箭牌）
- FDE 规则 §4「观测/队列/同步类改动不得影响取数主链路」的 no-op 降级**仅适用于旁路**（observability、审计队列、KB 同步等），不延伸到功能主逻辑。
- **功能通道的错误 = 用户必须看到的结果**。取数解析失败回抛候选是"显式暴露"，不是降级；查不到业务本体数据却回退去查系统表充数、云端知识库熔断却不标注 `degraded` 是降级掩盖——前者允许，后者禁止。
- 透明回退的合格标准：**可诊断**（标注回退原因与来源）+ **行为可区分**（评测/审计能分辨正常路径与回退路径），两者缺一即视为掩盖。

## 3. 评审与自检清单
- 提交含 `except ... 回退/兜底/默认返回` 的 diff 时，必须回答：这个失败**用户知道吗**？不知道就必须补提示或去掉分支。
- "先加个降级上线再说"不是工程决策，是缺陷延期——提醒需求方，由人（而非代码）决定是否降级。
