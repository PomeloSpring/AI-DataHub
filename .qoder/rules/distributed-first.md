# 分布式强制约束（多实例是默认前提，不是选项）— 强制规范

> 本项目由多服务（datamind=8001、datacatalog=8005、semanticservice、dataflow、authservice…）+ 多副本可能共同部署。
> **"现在只跑一个实例"不是设计豁免理由。** 任何新逻辑必须先过"多实例拷问"，不满足的存量代码视为待改造缺陷。

## 1. 状态与协调：进程内状态即缺陷源
- **跨请求/跨实例共享的状态一律落共享层**：MySQL（`adh_*` 表，如 `adh_qoder_session`、`adh_ontology_kb_sync_state` 水位线）或 Redis（`REDIS_URL` 已编排，见 `services/docker-compose.yml`：限流、熔断计数、锁、去重、进度）。
- 进程内 dict/全局变量只允许两类用途：① 无一致性要求的只读缓存（可接受各实例短暂分歧，且写明失效策略）；② 单请求内的局部聚合。其余皆须外置。
- 典型反模式（发现即改造）：熔断器计数只存内存（多实例各自为政，N 副本= N 套熔断判断）、任务进度/会话/审批状态放进程内、`jieba.cache`/本地文件当跨实例真值源、依赖本地临时文件做服务间通信。
- 互斥/幂等敏感操作（同步、水位线推进、审批执行）必须用**分布式锁或 DB 乐观锁**（`SELECT ... FOR UPDATE` / 唯一键 / version 字段），禁止 `if not _inflight: _inflight = True` 式进程内防重。

## 2. 无状态执行与路由
- 服务实例必须可水平扩展：请求亲和性不得承载正确性状态（SSE/执行流断线重连必须能从共享层恢复或明确失败，不得依赖"还连着同一实例"）。
- 长任务（`adh_scheduled_*`、KB 同步、本体级联）以**任务表为唯一队列真值**，实例认领用条件更新（claim），崩溃后其他实例可接管；禁止"内存线程池里有谁在跑"式调度。
- 新增端点/服务必须假设前置负载均衡：流式接口的缓冲与重放走共享层（Redis stream/pubsub 或 DB），单播内存队列不合格。

## 3. 一致性与时间
- **幂等是默认要求**：审批执行、别名回写、KB 推送、同步水位线推进，重复投递不得产生重复副作用（唯一键/幂等键/水位线比较三选一必须有）。
- 时间一律服务端生成、存 UTC、比较用同一时钟源；跨实例不得依赖本地时钟排序做裁决（用自增 id / 版本号 / Redis INCR）。
- 派生系统（图谱、qmind 文档、绑定表）一致性靠**级联 + 水位线 + reconcile 对账**收敛，禁止"本地改完就算完"。

## 4. 存量改造与评审门禁
- 碰到上述反模式的存量代码且当前任务与其相关，**必须改造**（状态外置 / 加锁 / 补幂等），并在 PR 说明改造点；不得在新功能里继续"沿用旧写法"扩大单实例假设。
- 改造涉及无 `--reload` 常驻服务时按既有规矩重启对应服务；多实例行为变更须给出验证方式（起两实例并发跑该路径的说明或测试）。
- 评审快查（任一为"否"即不满足本规则）：状态在共享层吗？两实例同时执行这段代码结果一致吗？进程重启/换实例后还能恢复吗？
